- 실제 앱 스크린샷은 증거로 유지하되, 단순 화면 나열이 아니라 사용 흐름과 구현 상태를 설명하는 용도로 재배치했다.
- 완성된 부분과 운영 검증 중인 부분을 분리해서 말하도록 구현 현황 장을 추가했다.

## 발표 메모

### 1. KBO Fans

- 첫 장에서는 앱 이름보다 한 줄 가치를 먼저 말한다.
- "내 팀 경기와 경기 맥락을 한 손에"라는 방향으로 홈, 문자중계, 기록실 화면을 묶어 소개한다.

### 2. 서비스 개요

- 사용자는 야구를 하루에 한 번만 확인하지 않는다.
- 오전/점심, 경기 전, 경기 중, 경기 직후, 다음 날로 이어지는 질문을 보여주고 앱이 맡을 역할을 설명한다.

### 3. 문제 / 기회

- 종합 스포츠 앱, 공식/통계 앱, 개인 중계 앱이 각각 장점은 있지만 반복 사용 루프를 한 앱에서 닫지 못한다는 점을 말한다.
- KBO Fans의 위치는 "야구만 보는 앱, 내 팀을 먼저 보여주는 앱, 필요할 때 깊어지는 앱"이다.

### 4. 제품 구조

- 마이팀 선택이 단순 설정값이 아니라 홈, 상세, 일정, 알림의 기본 문맥이라는 점을 강조한다.
- 온보딩과 홈 반영 화면을 함께 보여준다.

### 5. 홈

- 홈은 뉴스 피드가 아니라 오늘의 경기판이다.
- 마이팀 브리프, 오늘 경기 카드, 상세/알림/기록으로 넘어가는 관문 역할을 설명한다.

### 6. 경기 상세

- 스코어, 문자중계, 박스스코어, 라인업을 하나의 경기 맥락으로 설명한다.
- "점수 -> 왜 그런지 -> 누가 만들었는지" 흐름으로 말하면 기능 나열처럼 들리지 않는다.

### 7. 경기 후 기록

- 라이트팬은 순위와 결과를 빠르게 확인하고, 코어팬은 기록실과 리더보드까지 들어간다.
- 경기 후 관심이 시즌 흐름과 선수 기록으로 이어진다는 점을 말한다.

### 8. 경기 전 준비

- 일정 화면은 단순 달력이 아니라 경기 전 준비 흐름의 시작이다.
- 경기 확인, 상대/시간/구장 확인, 예매 알림 준비로 설명한다.

### 9. 알림

- 알림을 "모두 켜는 기능"이 아니라 "팬이 놓치고 싶지 않은 순간을 고르는 구조"로 설명한다.
- 앱 종료 후 push / Live Activity 갱신은 운영 backend가 필요한 범위라고 분리해서 말한다.

### 10. 데이터 처리

- Backend는 API-backed data, snapshot generation, scheduler, push, Live Activity / Dynamic Island sync를 담당하는 active runtime component다.
- Direct KBO mode는 local/offline preview와 resilience 검증용으로 유지한다.
- 화면 데이터 API 검증은 `USE_BACKEND_API=true`, endpoint 설정은 `API_BASE_URL`로 분리해 주입한다는 점을 말한다.

### 11. 구현 현황

- 발표 가능한 화면과 검증 중인 운영 범위를 숨기지 않고 나눠 말한다.
- 화면 경험과 개인화는 발표 가능/구현으로 말한다.
- 데이터 경로는 backend-backed / direct mode 분리로 말하고, 알림/앱 밖 표면과 배포는 운영 검증 중으로 말한다.

### 12. 다음 단계

- 다음 단계는 보는 앱에서 경기를 따라가는 앱으로 확장하는 것이다.
- 실기기 push 안정화, 마이팀 Live Activity, 기록실 깊이 보강, 예매/기록 알림을 짧게 정리한다.
